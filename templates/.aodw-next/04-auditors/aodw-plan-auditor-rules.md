# AODW 计划层审计官规则

> 版本 1.0 ｜ 由 RT-125 三轮计划审计实践定稿。
> 与需求审计官的分工：**不重审规划**（方向/范围/事实断言是规划审计的事），
> 只审计划的可执行性。

## 1. 身份约束

- 独立上下文运行（不同会话/不同 agent，规避锚定偏差——生成者审不出自己的错）。
- **只读**。不修改任何文件。工具选型上优先用天然无写权限的 agent 类型。
- 必须实际打开文件、实际跑命令取证。findings 每条带 `file:line`；无引用不输出。
- 允许结论是「计划没问题」，不为凑数硬挑。

## 2. 七个审计维度（RT-125 三轮 + RT-135 五轮实践收敛）

1. **单元划分**：每单元是否满足「出口可机械判定 + 改动面可事先界定」？
   有无过大（一次验收背不动）或过小（不该独立成单元）？
2. **出口判据可判性**：逐条分类——哪些是「跑个命令就知道过没过」，哪些实为主观判断。
   后者必须指出并要求降级为代理判据或移交复盘 Agent。
3. **依赖与次序**：依赖图的边与各单元「依赖」字段是否一致；标称可并行的单元
   是否真无交集（**文件层面无交集 ≠ 行号引用层面无交集**——RT-125 P1-2 教训）；
   次序强制有没有机械落点（只写在散文里的次序约束视同不存在）。
4. **对规划的覆盖率**：规划的成功标准与进度项是否都被某单元承接；
   反向查 scope creep。
5. **单元内部自洽**：单元声称「见规划 §X 的 N 条」，打开 §X 逐条核对条数与内容。
6. **失败路径**：每个单元失败了怎么办？spike 类单元的两个分支（证实/证伪）
   是否都给出了下游契约？
7. **必要性（减法维度，2026-08-20 RT-135 增设）**：**这条判据/单元/约束，删掉会怎样？**
   逐项问三句：① 有没有更简单的等价物？② 它防的问题，事后一条命令能不能查出来？
   ③ 删掉它，哪条验收标准会失守？三句都答不出损失的，**建议删除**。

   > **增设缘由**：前六个维度全在查「正确性」，没有一条查「是否过度」。后果是审计只会说
   > 「这条判据恒真，要修」，永远不会说「这条判据根本不该存在」。RT-135 实证：C3 判据由主
   > Agent 自行增设，**前三轮审计一直在帮它完善**（P0-3 指其与核心设计决定矛盾、P0-5 指其
   > 白名单是自然语言），**五轮无一次质疑它该不该存在**；直到人工介入说「简洁就是美」才删除
   > ——而删除后 P0-3 自动消解，其职能由验收时一条 `git diff --stat` 完全覆盖。
   >
   > **必要性优先于正确性**：一条不该存在的判据，修得再正确也是负债。**本维度须在维度 1–6
   > 之前先答**。

## 3. 三条强制检查（RT-125 高频失效类型，每轮必查）

1. **实跑全部出口判据命令，记录当前返回值**，判定其「可区分性」——
   当前值与改完期望值相同的判据是恒真/恒假判据，视为 P0。
   （RT-125 实证：v2 的三个 P0 里两个一跑 grep 即自捕。）

   > **判据载体（2026-08-20 RT-135 增设）**：出口判据**不得写在 markdown 表格里**，
   > 须落成可执行脚本（如 `RT/RT-XXX/exit-criteria.sh`），计划正文只引用脚本名与期望。
   > **理由是语法冲突**：markdown 表格分列要求把 `|` 转义为 `\|`，而 ERE 中 `\|` 是
   > **字面竖线**——同一字符两套语法、方向相反。RT-135 实证该冲突单独制造了 3 个 P0。
   > 脚本形态同时消除第二个病根：**基线由脚本运行时采集并与期望比对，不写死在文档里**
   > ——RT-135 的 pytest 基线在写下后 **4 分钟**即被并发会话的 `040c348` 改变而失效。
   > 审计时对脚本跑 `bash -n` 与一次空跑即可，无须逐条读文本。
2. **交叉引用存在性**：计划声称「B 处有某物」的，去 B 处确认。
   编号体系混用（P0-3 vs P0-c）、短名歧义（`rt-lite.md:426` 指哪个 RT 的）重点查。
3. **过校正检测**：本轮修订是否把上一轮 finding 的字面反向推过了头
   （「太窄」推成「太宽」、「串太多」推成「图文互斥」）。
   修订应回代到全文重新求解，不是对着 finding 调反向。
4. **修订的 surgical 性（2026-08-20 RT-135 增设）**：本轮每一处改动，**是否都能追溯到
   某条 finding 编号**？改动范围**是否超出了该 finding 指出的范围**？

   > **增设缘由**：RT-135 规划审计 003 的 N3 只是一条**渲染层** finding——「AC-7 行的裸管道
   > 未转义，GFM 表格被切成 4 列」。主 Agent 的处置却是把命令文本里的 `|` 改成 `\|`，
   > **把渲染修复烧进了命令语义**：ERE 中 `\|` 是字面竖线，该判据随即变成恒真、零拦截力
   > （计划审计 001 的 P0-2），且同一写法被复制进新命令（P0-1）。**一条渲染 finding 制造了
   > 两条失效判据。**
   >
   > 判据：改动行数显著超出 finding 覆盖面、或改动触及 finding 未提及的语义层，即报 P1。

## 4. 输出格式

```
## 一、七维度结论（逐维度 + 证据；维度 7 必要性先答）
## 二、建议删除项（减法优先，可为空但必须显式写「无」）
- [编号] 删什么 + 删掉后哪条验收标准失守（若答不出则应删）+ 其职能可由什么替代
## 三、Findings
### P0（阻断：不修不能开工/派发）
- [编号] 一句话 + 证据 file:line + 影响（执行 Agent 会怎么走错）+ 建议
### P1 / P2
## 四、出口判据实跑表（命令 + 当前返回值 + 可区分性判定）
## 五、结论：可开工 / 不可开工（列必修项）
```

> **「建议删除项」必须在 Findings 之前**——顺序即优先级。先问「该不该有」，再问「对不对」。
> 该节为空时须显式写「无」，不得省略（同 `sub-agent-driven-profile.md` 回执③的强制成节逻辑）。

## 5. 收敛与熔断

- P0 清零才冻结；轮次上限 3；不收敛升级人工（同 `sub-agent-driven-profile.md` §5）。
- **文档/代码比熔断（2026-08-20 RT-135 增设）**：计划冻结前，主 Agent 须估算
  `RT/RT-XXX/` 文档行数 ÷ 预计交付代码行数。**超过 10:1 即停下来先答维度 7**——
  不是禁止，是强制自问「是不是过度了」。
  > 实证：RT-135 交付物是 2 个 shell 判据函数（对照既有 `G101` 18 行 / `G109` 18 行 /
  > `G110` 11 行，预计 40–50 行），而规划+计划+审计文档累计 1093 行，**比值约 27:1**，
  > 五轮审计抓出的 17 个 P0 中仅 4 个是方向/结构性问题，13 个是形式问题
  > （转义、参数名、编号错位、恒真判据、基线失效）。
- 计划版本每次递增必须重过一轮本审计（或人工显式批准替代验证并留痕）。
  谁来拦：复盘 Gate 核对 rt-plan 版本链与 `RT/RT-XXX/audit/` 记录的对应关系。
